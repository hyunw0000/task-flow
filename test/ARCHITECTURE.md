# 아키텍처: 카드형 Task 관리 웹 앱

- 작성일: 2026-10-19
- 출처: [PRD.md](PRD.md), [PRODUCT-DIRECTION.md](PRODUCT-DIRECTION.md), PRD 를 화면 · API · 저장소 · 공통 검증으로 나눈 표
- 결정 기록: [DECISIONS.md](DECISIONS.md). 이 문서의 (D-xxx) 는 그 문서의 결정 번호다.
- ID 표기: R-xxx 는 PRD 의 요구사항, R-xxx.n 은 그 요구사항의 n 번째 완료 조건, V-n 은 공통 검증 규칙, Q-xx 는 열린 질문이다.

## 1. 전체 모양

한 사람이 자기 컴퓨터에서 세 부분을 함께 실행한다. 기술은 PRODUCT-DIRECTION.md 의 표준 경로만 쓴다. (F-04, D-001)

```
┌──────────────────────┐   HTTP (JSON)   ┌──────────────────────┐   SQL   ┌──────────────────┐
│ 화면                 │ ──────────────▶ │ API                  │ ──────▶ │ 저장소           │
│ React · Vite         │ ◀────────────── │ FastAPI              │ ◀────── │ SQLite 파일 하나 │
│ (브라우저)           │   /api/...      │ (로컬 프로세스)      │         │                  │
└──────────────────────┘                 └──────────────────────┘         └──────────────────┘
```

- 화면은 저장소에 직접 닿지 않는다. 모든 읽기와 쓰기는 API 를 거친다. (D-002)
- 카드의 원본은 저장소 하나뿐이다. 화면이 들고 있는 카드는 API 에서 받은 사본이다. (D-003, R-006.1)
- 개발 중에는 Vite 개발 서버가 `/api` 로 시작하는 요청을 FastAPI 로 넘긴다. 브라우저 입장에서는 주소가 하나다. (D-010)

## 2. 화면 구조

```
frontend/

├── vite.config.js          # /api 요청을 API 로 넘기는 설정 (D-010)
└── src/

    ├── App.jsx             # 카드 목록 상태를 들고, 처음 열 때 API 에서 불러온다
    ├── api/
    │   └── cards.js        # API 호출을 모은 곳. 화면의 다른 부분은 fetch 를 직접 쓰지 않는다
    ├── domain/
    │   ├── status.js       # 상태 세 가지의 코드와 화면 이름 (D-006)
    │   └── validation.js   # 화면 쪽 사전 검사 (V-1)
    └── components/
        ├── StatusView.jsx  # 상태별 보기. 모양은 Q-05 에 따라 정한다
        ├── StatusGroup.jsx # 상태 하나에 속한 카드 묶음
```

- 화면 상태는 React 의 기본 기능(컴포넌트 state)만으로 관리한다. 별도 상태 관리 도구를 들이지 않는다. (D-011)
- 화면은 변경 요청이 성공한 뒤에만 화면에 반영한다. 미리 반영했다가 되돌리지 않는다. (D-003)

### 요청 목록 (D-005, D-007)

| 요청 | 하는 일 | 성공 응답 | 근거 |
| --- | --- | --- | --- |
| `GET /api/cards` | 모든 카드를 돌려준다 | 200, 카드 배열 | R-003.1, R-006.1 |
| `POST /api/cards` | 카드를 만든다 | 201, 만든 카드 | R-001.1 |
| `PATCH /api/cards/{id}` | 제목 · 설명을 고친다. 상태는 받지 않는다 | 200, 고친 카드 | R-004.1, R-002.3 |
| `PATCH /api/cards/{id}/status` | 상태를 바꾼다 | 200, 바꾼 카드 | R-002.1 |

### 카드 응답 모양

```json
{
  "id": 1,
  "title": "보고서 초안 쓰기",
  "description": "",
  "status": "todo",
  "created_at": "2026-10-19T10:00:00Z",
  "updated_at": "2026-10-19T10:00:00Z"
}
```

- `status` 는 `todo` · `in_progress` · `done` 가운데 하나다. 화면은 이를 할 일 · 진행 중 · 완료로 보여 준다. (D-006)
- 목록은 페이지를 나누지 않고 한 번에 돌려준다. (D-008)

## 4. 저장소 구조

SQLite 파일 하나에 테이블 하나를 둔다.

```sql
CREATE TABLE IF NOT EXISTS cards (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    title       TEXT    NOT NULL CHECK (length(trim(title)) > 0),
    description TEXT    NOT NULL DEFAULT '',
    status      TEXT    NOT NULL CHECK (status IN ('todo', 'in_progress', 'done')),
    created_at  TEXT    NOT NULL,
    updated_at  TEXT    NOT NULL
);
```

| 칸 | 정한 것 | 근거 |
| --- | --- | --- |
| `id` | 저장소가 매기는 정수. 수정 · 상태 변경 · 삭제의 대상을 가리킨다 | D-007 |
| `title` | 비어 있으면 저장되지 않는다. API 검증이 뚫려도 저장소가 마지막으로 막는다 | V-1, D-004 |
| `description` | 비어 있으면 빈 문자열로 저장한다. 비워도 되는지는 Q-01 | D-012 |
| `status` | 세 값 가운데 정확히 하나. 비어 있을 수 없다 | V-2, V-3, D-006 |
| `created_at` · `updated_at` | 같은 상태 안의 기본 순서(만든 순서)에 쓴다. 최종 순서는 Q-06 | D-013 |

- 앱을 시작할 때 테이블이 없을 때만 만든다. 이미 있는 파일과 데이터는 그대로 이어 쓴다. (R-006.2, D-009)
- 삭제는 행을 실제로 지운다. 되살리기는 Q-07 에 따라 바뀔 수 있다. (D-014)

## 6. 데이터 흐름

### 6.1 Task 등록 (R-001)

```
사용자          CardForm / App          api/cards.js        FastAPI (routes · schemas)     repository · SQLite
  │ 제목·설명 입력 → 등록 │                   │                        │                              │
  │ ─────────────────────▶│ V-1 사전 검사     │                        │                              │
  │                       │ ─────────────────▶│ POST /api/cards        │                              │
  │                       │                   │ ──────────────────────▶│ V-1 · V-2 검사               │
  │                       │                   │                        │ ────────────────────────────▶│ INSERT, 커밋
  │                       │                   │                        │ ◀────────────────────────────│ 새 행
  │                       │                   │ ◀──────────────────────│ 201 + 만든 카드              │
  │                       │ ◀─────────────────│                        │                              │
  │ ◀─────────────────────│ 목록에 넣고 상태별 보기에 표시              │                              │
```

1. 사용자가 `CardForm` 에 제목과 설명을 넣고 등록한다.
2. 화면이 V-1(제목 비어 있지 않음)을 먼저 검사한다. 비었으면 요청을 보내지 않는다. → 7.1
3. `api/cards.js` 가 `POST /api/cards` 로 `{ title, description }` 을 보낸다.
4. `schemas.py` 가 V-1 을 다시 검사한다. 처음 상태는 `todo` 로 정한다. (D-012, Q-02)
5. `repository.py` 가 한 트랜잭션으로 행을 넣고 커밋한다. 커밋이 끝난 뒤에야 응답한다. (R-006.3)
6. API 가 `201` 과 만든 카드를 돌려준다.
7. `App` 이 받은 카드를 목록에 넣는다. `StatusView` 가 새 카드를 처음 상태 쪽에 보여 준다. (R-001.3)

### 6.2 상태 변경 (R-002)

```
사용자        StatusPicker / App        api/cards.js          FastAPI (routes · schemas)     repository · SQLite
  │ 새 상태 고름 │                         │                          │                              │
  │ ────────────▶│ ───────────────────────▶│ PATCH /api/cards/{id}/status                           │
  │              │                         │ ────────────────────────▶│ V-2 검사, 카드 있는지 확인   │
  │              │                         │                          │ ────────────────────────────▶│ UPDATE status, 커밋
  │              │                         │ ◀────────────────────────│ 200 + 바꾼 카드              │
  │              │ ◀───────────────────────│                          │                              │
  │ ◀────────────│ 카드를 새 상태 쪽으로 옮겨 표시                     │                              │
```

1. 사용자가 `StatusPicker` 로 세 상태 가운데 하나를 고른다. 화면은 세 값 밖의 값을 만들 수 없다. (V-2)
2. `api/cards.js` 가 `PATCH /api/cards/{id}/status` 로 `{ status }` 를 보낸다.
3. `schemas.py` 가 V-2 를 검사한다. `routes` 가 해당 카드가 있는지 확인한다. (V-5, 추론)
4. `repository.py` 가 `status` 와 `updated_at` 만 바꾸고 커밋한다. 제목 · 설명은 건드리지 않는다.
5. API 가 `200` 과 바꾼 카드를 돌려준다.
6. `App` 이 목록의 그 카드를 응답으로 바꾼다. `StatusView` 가 카드를 새 상태 쪽에 한 번만 보여 준다. (R-002.2, R-003.2)

- 상태는 이 요청으로만 바뀐다. 제목 · 설명 수정 요청(`PATCH /api/cards/{id}`)은 `status` 를 받지 않는다. (V-4, R-002.3, D-005)
- 상태를 옮기는 순서 제한(Q-03)은 아직 없다. 생기면 3 단계의 검사에 더한다.

## 7. 실패 흐름

모든 실패에서 공통으로 지키는 것: **실패한 변경은 화면에도 저장소에도 반영되지 않는다.** 화면은 성공 응답을 받았을 때만 목록을 고친다. (D-003)

API 오류 응답은 FastAPI 기본 형식인 `{ "detail": ... }` 을 쓴다. (D-015)

| # | 실패 | 어디서 잡나 | API 응답 | 화면이 하는 일 | 근거 |
| --- | --- | --- | --- | --- | --- |
| 7.1 | 제목이 비어 있다 (공백만 있는 경우 포함) | 화면 사전 검사 → API `schemas` → 저장소 CHECK | 422 | 요청을 보내지 않거나 실패를 알린다. 입력한 내용은 지우지 않는다. 보여 줄 문구는 Q-11 | V-1, R-001.2, R-004.2 |
| 7.2 | 상태 값이 세 가지 밖이다 | API `schemas` → 저장소 CHECK | 422 | 화면은 세 값만 고르게 하므로 정상 사용에서는 생기지 않는다. 생기면 실패를 알린다 | V-2 |
| 7.3 | 수정 요청에 `status` 가 들어 있다 | API `schemas` | 422 | 화면은 보내지 않는다 | V-4, D-005 |
| 7.4 | 대상 카드가 없다 (이미 지워짐 등) | API `routes` | 404 | 실패를 알리고 `GET /api/cards` 로 목록을 다시 불러온다 | V-5 (추론, Q-17 후보) |
| 7.5 | API 에 연결되지 않는다 (API 를 실행하지 않음 등) | 화면 `api/cards.js` | — | 연결 실패를 알린다. 처음 열 때라면 빈 보기 대신 실패 상태를 보여 준다. 입력한 내용은 지우지 않는다 | R-006.1 |
| 7.6 | 저장소 쓰기가 실패한다 (파일 잠김 · 디스크 문제 등) | `repository` | 500 | 트랜잭션을 되돌린다. 화면은 실패를 알리고 목록을 고치지 않는다 | R-006.3 |
| 7.7 | 앱 시작 때 저장소 파일이 없다 | `db.py` | — | 빈 저장소를 새로 만든다. 파일이 있으면 그대로 이어 쓴다 | R-006.2, D-009 |

- 같은 컴퓨터에서 탭을 여러 개 열어 한쪽 탭의 목록이 낡은 경우는 아직 다루지 않는다. 7.4 의 "다시 불러오기"가 일부를 덮는다. (Q-14, A-02)

## 8. 열린 질문이 이 구조에 주는 영향

| 질문 | 답에 따라 바뀌는 곳 |
| --- | --- |
| Q-01 설명 비움 | `schemas.py` 검증, `description` 칸 규칙 (D-012) |
| Q-02 처음 상태 | `POST /api/cards` 본문에 `status` 를 받을지, `CardForm` 에 `StatusPicker` 를 둘지 (D-012) |
| Q-03 순서 제한 | `PATCH /api/cards/{id}/status` 검사, `StatusPicker` 선택지 |
| Q-04 상태 바꾸는 방법 | `StatusPicker` 의 모양만 바뀐다. API 는 그대로다 |
| Q-05 보기 모양 · Q-15 화면 크기 · Q-16 카드 표시 정보 | `StatusView` · `StatusGroup` · `CardItem` 만 바뀐다 |
| Q-06 카드 순서 | 사용자가 순서를 바꿀 수 있어야 하면 `cards` 에 순서 칸과 요청이 더 생긴다 (D-013) |
| Q-07 삭제 확인 · 되살리기 | 확인은 화면만, 되살리기는 저장소 삭제 방식이 바뀐다 (D-014) |
| Q-08 길이 제한 | `schemas.py` · `validation.js` · 저장소 CHECK |
| Q-09 수정에서 상태 | `PATCH /api/cards/{id}` 와 V-4 (D-005) |
| Q-11 실패 문구 | 화면의 실패 표시만 바뀐다 |
| Q-12 상태 고정 | 고정이 아니면 상태를 테이블로 빼야 한다 (D-006) |
| Q-13 카드 수 | 많으면 목록 나누기가 필요하다 (D-008) |
| Q-14 탭 여러 개 | 낡은 목록 감지 방식이 더 필요할 수 있다 |
