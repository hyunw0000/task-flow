# PRD: 미팅플레이스

- 상태: 초안 (2차 개정)
- 작성일: 2026-10-20
- 출처: [../MEETING-PLACE-PLAN.md](../MEETING-PLACE-PLAN.md), 경쟁 서비스 조사(위밋플레이스, 야만나 등)
- ID 표기: R-xxx 는 요구사항, A-xx 는 가정, Q-xx 는 열린 질문이다.
- 개정 내용: 실시간 위치 공유를 1차 범위에 넣었다. 주변 밥집·술집 찾기를 메인 기능으로, 이동시간 공평성은 기본 기능으로 정리했다.

## 1. 한 문장 설명

모임 사람들이 서로의 위치를 실시간으로 보면서, 모두에게 가까운 곳 주변의 밥집·술집을 찾아 투표로 정하는 웹 앱이다.

## 2. 기능의 무게

| 구분 | 기능 | 설명 |
| --- | --- | --- |
| 메인 | 주변 밥집·술집 찾기 | 모두의 위치를 기준으로 한 지점 주변의 식당·술집·카페를 찾아 추천하고 고르게 한다. |
| 메인 | 실시간 위치 공유 | 참가자가 동의하면 서로의 현재 위치를 지도에서 실시간으로 본다. |
| 기본 | 거리 공평성 | 모두의 이동시간이 비슷한 지점을 기준으로 삼는다. 당연히 되어야 하는 기능이라 따로 내세우지 않는다. |
| 보조 | 공통 거리 표시 | 참가자 사이의 거리와 모두가 모이는 지점까지의 거리를 지도에 나타낸다. |
| 보조 | 투표 | 후보 장소를 올리고 투표로 정한다. |

## 3. 배경과 차별점

- 비슷한 서비스가 이미 있다. 위밋플레이스(앱·웹)와 야만나(웹)는 중간 지점을 계산하고 주변 장소를 보여 준다.
- 두 서비스는 정적인 계산 결과를 한 번 보여 주는 데서 끝난다. 서로의 위치를 실시간으로 보며 장소를 정하는 서비스는 이번 조사에서 확인하지 못했다.
- 위밋플레이스에는 "중간 거리만 찍어 준다. 놀 만한 곳이 아니다"라는 사용자 불만이 있었다. 이 앱은 장소 추천을 중심에 둔다.
- 조사한 정보 중 일부는 출처 신뢰도가 낮다. 가격 정책 같은 세부 사항은 확인하지 못했다.

| 차별점 | 내용 |
| --- | --- |
| 실시간 위치 | 이동 중인 서로의 위치를 지도에서 본다. "지금 어디쯤이야?"가 필요 없다. |
| 장소 추천 중심 | 거리 계산이 아니라 갈 만한 밥집·술집을 고르는 데 쓴다. |
| 링크로 각자 참여 | 한 사람이 친구들 위치를 입력하지 않아도 된다. |
| 투표로 확정 | 후보를 올리고 참가자가 투표해 정한다. |

## 4. 사용자와 상황

- **사용자**: 2~6명이 서로 다른 곳에서 출발해 만날 장소를 정하려는 친구 · 동료 모임이다. (A-01)
- **사용 방식**: 모임 만든 사람이 링크를 공유하고, 참가자는 링크를 열어 위치 공유에 동의하고 참여한다. 휴대폰 브라우저가 중심이다. (A-02)
- **로그인**: 1차에는 없다. 링크를 아는 사람이 참가한다. (A-03)
- **지역**: 한국이다. 국내 지도와 대중교통 API를 쓴다.

## 5. 목표

- 모임 사람들이 서로의 위치를 보며 만날 장소를 빠르게 정한다.
- 모두에게 적당한 곳 주변에서 갈 만한 밥집·술집을 바로 찾는다.
- 채팅방에서 링크 하나로 참여부터 투표까지 끝낸다.

## 6. 비목표 (1차에서 하지 않는다)

- 회원가입, 로그인, 모임 재사용(자주 만나는 그룹 저장)
- 자동차 이동시간. 대중교통만 다룬다. (결정 필요 → Q-02)
- 예약, 결제, 리뷰 작성
- 네이티브 앱. 웹으로 시작한다. 한계는 7장에 적었다.
- 화면을 꺼도 위치가 계속 공유되는 백그라운드 추적

## 7. 범위

### Must (1차)

| ID | 기능 | 내용 |
| --- | --- | --- |
| R-001 | 모임 만들기 | 모임 이름과 상황(점심, 저녁, 2차)을 정하고 공유 링크를 만든다. |
| R-002 | 참여와 동의 | 참가자가 링크를 열고 이름을 입력한 뒤 위치 공유에 동의한다. 동의 전에는 위치를 보내지 않는다. |
| R-003 | 실시간 위치 공유 | 동의한 참가자의 현재 위치를 서버에 주기적으로 보내고, 다른 참가자의 지도에 실시간으로 표시한다. |
| R-004 | 공유 중지 | 참가자가 언제든 위치 공유를 끌 수 있다. 끄면 마지막 위치도 지도에서 사라진다. |
| R-005 | 기준 지점 계산 | 모두의 이동시간이 비슷한 지점(지하철역·번화가 후보 5~10곳 중 최대 이동시간이 짧은 곳)을 기준 지점으로 삼는다. 참가자 위치가 바뀌면 다시 계산한다. |
| R-006 | 주변 밥집·술집 찾기 | 기준 지점 주변의 음식점·술집·카페를 카테고리별로 찾는다. 거리, 평점, 영업 여부를 보여 준다. |
| R-007 | 상황 프리셋 | 점심, 저녁, 2차를 고르면 카테고리와 정렬 기준이 바뀐다. |
| R-008 | 공통 거리 표시 | 지도에 참가자 사이 거리와 각자에게서 기준 지점·후보 장소까지의 거리·이동시간을 나타낸다. |
| R-009 | 후보 투표 | 마음에 드는 장소를 후보로 올리고 참가자가 투표한다. 모임 만든 사람이 확정한다. |
| R-010 | 링크 공유 | 링크를 복사해 카카오톡 등에 붙여 넣을 수 있다. |

### Later (2차 이후)

| 항목 | 메모 |
| --- | --- |
| 백그라운드 위치 공유 | 웹으로는 한계가 있다. 네이티브 앱이 필요하다. |
| 환승 횟수 반영 | ODsay에서 환승 정보를 받을 수 있는지 확인 필요. |
| 모임 재사용 | 로그인과 개인정보 문제가 따른다. |
| 자동차 이동시간 | 카카오모빌리티 길찾기 |
| 카카오톡 공유 버튼 | 카카오 SDK 연동 |

### 실시간 위치 공유의 기술 한계

- 브라우저의 위치 API(`navigator.geolocation`)는 HTTPS에서만 동작하고 사용자가 권한을 허용해야 한다.
- 웹 페이지가 백그라운드로 가거나 화면이 꺼지면 위치 갱신이 끊긴다. 1차에서는 "앱 화면을 켜 두는 동안 공유된다"를 전제로 한다. 이 점을 화면에 안내한다. (A-05)
- 서버는 위치를 받아 다른 참가자에게 전달해야 한다. FastAPI의 WebSocket 또는 SSE를 쓴다. (결정 필요 → Q-10)

## 8. 위치 정보와 개인정보

- 위치 정보는 민감하다. 위치정보법 적용 여부와 약관·동의 요건은 공개 전에 확인해야 한다. (Q-03)
- 위치 공유는 참가자가 모임별로 동의해야 시작한다. 동의 기본값은 꺼짐이다. 동의는 언제든 철회할 수 있다. (R-002, R-004)
- 실시간 위치는 같은 모임 참가자에게만 보인다. 링크가 새어 나갈 때를 대비해 모임 만든 사람이 참가자를 내보낼 수 있게 할지 정해야 한다. (Q-11)
- 지도에 보이는 정밀도를 정확한 위치로 할지, 대략적인 위치로 뭉갤지 정해야 한다. (Q-05)
- 모임이 끝나면 위치 데이터를 지운다. 보관 기간은 Q-04에서 정한다.
- 위치 이력은 기본적으로 저장하지 않고 마지막 위치만 보관하는 것을 원칙으로 한다. (A-06)

## 9. 외부 서비스

| 용도 | 서비스 | 비고 |
| --- | --- | --- |
| 지도 | 카카오맵 JS SDK | 도메인 제한을 건다. |
| 주소 검색, 장소 검색 | 카카오 로컬 API | 음식점(FD6)·카페(CE7) 카테고리 검색. 평점·영업시간은 주지 않는다. |
| 평점, 영업시간 | Google Places API (New) | 이름·좌표로 매칭해 보강한다. 유료, 무료 한도 있음. |
| 대중교통 이동시간 | ODsay 또는 TMAP | 기준 지점 계산에 쓴다. 위치가 자주 바뀌므로 호출 한도에 주의한다. |

공식 API만 쓴다. 지도 화면을 크롤링하지 않는다.

## 10. 가정

- A-01: 모임 인원은 2~6명이다.
- A-02: 대부분 휴대폰 브라우저로 쓴다.
- A-03: 링크를 아는 사람은 누구나 참가할 수 있어도 1차에서는 문제없다.
- A-04: 대중교통 API의 무료 한도로 1차 시험이 가능하다.
- A-05: 사용자가 화면을 켜 두는 동안만 위치가 공유되어도 1차 목적에 충분하다.
- A-06: 위치 이력 없이 마지막 위치만 있으면 된다.
