## D-001 코드는 `meeting-place/` 폴더 안에 둔다

- 결정: `meeting-place/backend/`, `meeting-place/frontend/`를 만든다. 루트의 `backend/`·`frontend/`는 기존 task-flow 코드이므로 건드리지 않는다.
- 이유: 저장소를 새로 파지 않고 바로 시작할 수 있다. 기획 문서도 이미 이 폴더에 있다.
- 바뀔 조건: 별도 저장소로 가기로 하면 폴더째 옮긴다.

## D-002 표준 스택만 쓴다

- 결정: 화면 React·Vite, API FastAPI, 저장소 SQLite. 상태 관리 라이브러리, CSS 프레임워크, ORM은 들이지 않는다.
- 예외: 지도는 카카오맵 JS SDK를 `<script>`로 불러 쓴다.
- 이유: 한 사람이 만드는 1차 범위에 도구를 늘리면 유지 비용이 이득보다 크다.

## D-003 세 부분 나누기와 키 보관

- 결정: 화면은 외부 API를 직접 부르지 않는다. 장소 검색·평점·이동시간은 모두 FastAPI를 거친다.
- 예외: 카카오맵 JS 키는 브라우저에 있어야 하므로 도메인 제한을 건다.
- 이유: 키 유출과 호출 한도 초과를 서버에서 막는다.

## D-004 참가 토큰

- 결정: 참가하면 서버가 무작위 토큰을 주고, 브라우저가 `localStorage`에 저장한다. 이후 모든 요청에 토큰을 보낸다. 서버는 토큰의 해시만 저장한다.
- 이유: 로그인 없이 "같은 사람"을 알아보고, 같은 브라우저로 돌아오면 이름 입력 없이 복귀시킨다. 모임장 권한도 이 토큰으로 판단한다.
- 한계: 브라우저를 바꾸거나 저장소를 지우면 다른 사람으로 취급한다.

## D-005 실시간 전달

- 결정: 서버→화면은 SSE(Server-Sent Events), 화면→서버 위치 전송은 `PUT`으로 10초마다 한다. SSE로는 변경될 때마다 모임 전체 상태를 보낸다.
- 이유: 참가자 6명 이하라 전체 상태를 보내도 작다. WebSocket보다 구현이 단순하고 자동 재연결이 브라우저에 내장돼 있다.
- 바뀔 조건: 양방향 실시간(예: 채팅)이 필요해지면 WebSocket을 다시 검토한다.
- 주의: SSE는 헤더를 못 보내서 토큰을 쿼리(`?token=`)로 보낸다. 서버 로그에 쿼리가 남지 않게 한다.

## D-006 위치 정밀도

- 결정: 지도에는 참가자가 보낸 위치를 그대로 보인다.
- 이유: 목적이 "지금 어디쯤이야?"를 없애는 것이다. 뭉개면 목적이 약해진다.
- 대신: 동의 안내에 "모임 참가자에게 정확한 위치가 보입니다"를 분명히 적는다.

## D-007 대중교통만

- 결정: 1차는 대중교통 이동시간만 계산한다.
- 이유: 자동차를 넣으면 API와 UI 선택지가 늘어난다. 수도권 모임이 대중교통 중심이라는 가정이다.

## D-008 기준 지점

- 결정: 모든 참가자의 현재 위치 평균 근처에서 지하철역·번화가 후보 5~10곳을 뽑고, 후보별 참가자 이동시간을 구해 **최대 이동시간이 가장 짧은 곳**을 고른다. 최대값이 같으면 이동시간 편차가 작은 곳을 고른다. 자세한 규칙은 [BUSINESS-RULES.md](BUSINESS-RULES.md) BR-11·BR-15.
- 자동 재계산: 위치 변화가 크거나 참가자가 바뀌면 다시 계산한다. 모임장이 기준 지점을 고정하면 재계산을 멈춘다.
- 이유: 움직이는 사람 기준으로 매번 바뀌면 혼란스럽다. 고정 기능으로 모임장이 멈출 수 있게 한다.

## D-009 보관과 만료

- 결정: 모임 생성 24시간 뒤에 모임과 하위 데이터를 모두 지운다. 확정하거나 모임장이 끝내면 참가자 위치를 즉시 지운다.
- 위치 이력은 저장하지 않는다. 참가자 행에 마지막 위치 하나만 둔다. (A-06)
- 이유: 개인정보 부담을 줄이고 구현을 단순하게 한다.

## D-010 투표

- 결정: 한 사람이 1표를 갖고 다른 후보로 옮길 수 있다. 확정은 모임장이 하며 득표가 낮은 후보도 고를 수 있다.
- 이유: 동률과 마감 시각 문제를 사람이 정하게 해서 규칙을 줄인다.

## D-011 추천 정렬

- 결정: `점수 = 0.4×평점 + 0.3×거리 + 0.3×공평도`로 한다. 영업 중이 아닌 곳은 점수와 관계없이 뒤로 보낸다. 평점이 없으면 중립값을 쓴다. 계수는 [BUSINESS-RULES.md](BUSINESS-RULES.md) BR-14.
- 이유: 위밋플레이스의 불만("놀 만한 곳이 아니다")을 피하려면 평점이 가장 무거워야 한다. 계수는 써 보고 조정한다.

## D-012 캐시

- 결정: 장소 검색, 평점, 이동시간 결과를 SQLite `cache_entries`에 보관하고 종류별 유효 시간을 둔다.
- 이유: 위치가 자주 바뀌어 같은 질의가 반복되고, 무료 호출 한도가 작다.

## D-013 내보내기와 잠금

- 결정: 모임장은 참가자를 내보낼 수 있고 모임을 잠글 수 있다. 내보낸 참가자는 같은 모임에 다시 들어오지 못한다. 잠긴 모임은 새 참가를 받지 않는다.
- 이유: 링크가 새어 나갈 때 위치가 낯선 사람에게 보이지 않게 하는 최소한의 장치다.

## D-014 오류 형식

- 결정: 오류 본문은 `{ "detail": ... }` 이다. 입력 오류 422, 권한 없음 401·403, 없음 404, 충돌 409, 호출 과다 429, 외부 API 실패 502.

## D-015 Python과 uv

- 결정: Python 3.14, uv로 가상환경과 의존성을 관리한다. 기존 task-flow 백엔드와 같다.

## D-016 이동시간 API

- 결정: ODsay 대중교통 API를 먼저 쓴다. 호출 한도나 응답 문제가 있으면 TMAP 대중교통으로 바꾼다. 둘 다 한 파일(`services/transit.py`)에서만 부르게 해 바꾸기 쉽게 한다.
- 확인 필요: 환승 횟수가 응답에 있는지(Q-09)는 Later 항목이라 1차를 막지 않는다.
